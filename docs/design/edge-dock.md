# 收起横条贴边吸附

> **现状（2026-09-03）：** 形状 96×32 横书签头；判定模型是「**松手才吸**」。**架构定案：窗口交接**——落定闪烁根因经 GitHub 调研实锤为 Electron 结构性缺陷（可见时刻改透明窗尺寸，Chromium 合成器内容帧晚于 WindowServer 几何生效 1~N 拍，中间帧露空；官方 issue 2017→2025 全 not_planned；escrcpy/Qt/AHK 及 QQ/Snipaste/SideNotes 等成熟实现全部「恒定尺寸 + 纯位移」）。因此废除 union→96×32 裁窗，改为：书签头是**独立的 96×32 恒尺寸窗口**（预渲染、showInactive 上屏，像素与 DOM morph 末帧一致），交接后源便签窗隐藏；展开反向走同一套交接。不变量：**窗口可见时尺寸永远恒定**。union 生长 + 300ms DOM morph 动画、物理按键松手监视、悬停探头滑行全部保留。判定模型与外观不变。已随 [0.1.19](https://github.com/LawrenceChiu95/floating-sticky-notes/releases/tag/v0.1.19) 发布；Mac 真机已验收贴边吸附、快速甩边与落点长成展开。Windows 贴边未做 PC 真机验收。

## 背景

现有收起把便签变成仍留在桌面上的 40px 标题横条。横条置顶、可拖、可命名，但大部分时间挡在桌面或窗口上；截网页或应用窗口时也容易拍进去。

用户日常只在做完一件事时才需要把待办拖出来打勾，其余时间希望它像安全管家加速球一样吸在屏幕侧面，只露一条边。

本设计处理 [Issue #24](https://github.com/LawrenceChiu95/floating-sticky-notes/issues/24)。

## 目标

- 已收起的横条可以吸到当前屏幕左或右工作区边缘，收成一枚可拖的彩色书签头。
- 书签头静止时半藏在屏外（露 48px）；鼠标悬上去整条 96px 滑出贴边，移开滑回半藏。
- 不悬停也可以直接抓住半藏条往桌面里拖，松手后在落点长成上次展开的宽高（拉出回差带才展开，带内钉回）。
- 贴边状态写入 `notes.json`，重启后贴回原来那块屏的同一条边；只收成横条、未贴边的便签重启后仍展开。
- 贴边后截某个窗口或页面时，不再拍到 40px 横条。
- 贴边与现有收起共用同一个窗口控制器；**吸附与展开都是承诺式的「松手才执行」**（吸附 2026-08-21 定稿、展开 2026-09-01 修订）：拖动全程零写窗（横条/书签头跟手自由拖），拖进吸附区只显示「松手贴边」预览提示，物理松手确认后才执行 300ms DOM 逆揭示；展开同样等松手——窗口交接架构下途中展开要销毁书签头窗、原生拖拽会话随之中断（「拖到一半被迫停下再抓」被真机否掉），改为松手后按落点裁决：拉出回差带就在落点展开（340ms 揭示动画），带内就钉回。

## 非目标

- 不从展开态直接贴边，也不提供贴边回到横条的专用动作。
- 不吸顶边或底边。
- 不把横条收起状态写入 `notes.json`。
- 不调用 `setContentProtection` 或任何“从截图/录屏中排除窗口”的 API。
- 不做全局快捷键呼出、点击书签头展开。
- 不改变安装身份、`userData` 路径、开机启动或更新流程。
- 第一版不为多张贴边便签做智能分组；只在即将重叠时沿边错开，保证都能抓住。

## 已选方案

在现有收起控制器上增加第三态，窗口状态为：

`expanded` → `collapsed`（40px 横条）→ `docked`（左/右 96×32 横书签头）

三个态的窗口拖动全部走原生 `-webkit-app-region: drag`，与系统拖窗同一条路径——自定义拖窗（renderer 指针 + IPC 移窗、主进程轮询跟光标）在真机上始终比原生慢一拍，已废弃。拖动横条时主进程只判定吸附预览、不写窗；物理松手后才执行两次原生几何写入，中间可见运动全在 renderer。书签头拖动全程同样零写窗，松手后按落点一次裁决展开或钉回；180ms ease-out 滑行（`glideNoteWindowTo`）只用于拖拽已结束的悬停探头与中距钉回。

### 书签头 = 环 + 芯（悬停能进能出的关键）

macOS 上 `-webkit-app-region: drag` 的区域在**应用非激活时收不到 OS 的 enter/leave**（mousedown 与原生拖动不受影响），no-drag 区双向照收——2026-08-19 真机对照实验证实。用户悬停书签头时几乎都停在别的应用里，所以书签头不能整面 drag。结构（2026-08-21 二轮修订：四边环收成单侧条，修「边缘是小手却拖不动」）：

- 外壳 `.note-shell--docked` 永久 `no-drag`，承载便签色、圆角、名称视觉和一条轻微 CSS 内描边（不使用 CSS 外阴影），**只在朝桌面那一侧留 5px 传感条**（左贴边留右侧、右贴边留左侧）——光标从桌面横向进出必先跨这条 no-drag 条，应用非激活时 enter/leave 也能送达（对照实验 6/6）；
- 透明 `.dock-tab-pill` 是永久 drag 的拖动面，上下沿与壳齐平（`inset: 0 5px 0 0` / 右侧 `inset: 0 0 0 5px`），休息/探出都可直接抓取——书签头只有 32px 高，四边各 5px 的环曾吃掉 10px 高度，抓上下沿必中环；
- **光标诚实**：壳（含传感条）不是 drag 面，`cursor: default`；grab 只标在真能拖的 pill 上（旧版壳上挂 grab 小手却拖不动 = 光标撒谎）；
- 单侧条的代价：从上下沿贴屏边滑入时 first touch 落在 drag 面上，应用非激活会丢 enter——由 120ms 悬停复核轮询兜底（见下），事件只是快速通道。

半藏与露出纯靠窗口几何：窗口恒为 96 宽，休息位一半探出屏外（露 48px），露出位整条贴边；DOM 永远铺满窗口，进出贴边没有壳体尺寸过渡。多屏共边（隐藏半幅会漏到邻屏）时退回 48 宽全露。

### 悬停探头：事件只是扳机，光标真相说了算

- renderer 的 `mouseenter/leave` 只发 `sticky-notes:dock-peek` 意图；主进程每次都用一次性 `screen.getCursorScreenPoint()` 判定真实悬停再滑行（单次查询合法，红线是轮询跟光标做拖动）。
- 扳机撞上吸附/展开/探头滑行（inFlight）不丢：记下 pending，每次贴边态滑行收尾都用光标真相补一发 reconcile，「缩回途中光标折返」等断拍自愈。
- **悬停复核轮询（enter/leave 双兜底）**：OS 投递的 enter/leave 都不是 100% 可靠——应用非激活时 leave 会丢（实测快速甩出、贴屏边滑走），单侧传感条后从上下沿进入（落在 drag 面上）会丢 enter。贴边态全程每 120ms 比对「光标在窗内 ↔ 窗口已露出」，不一致就走与 enter/leave 相同的收缩/露出路径（reconcile 内部仍以光标真相为准）。只读光标位置、不逐帧驱动窗口，与被否的轮询拖窗无关；离开贴边态、展开、关窗即停。
- **抢拖熔断**：探头滑行途中用户抓住书签头抢拖时，第一帧偏离滑行走廊（y 偏 >2px 或 x 出 [minX-2, maxX+2]）的 move 就熔断滑行、把几何交还拖拽——原生拖拽会话进行中争写 setBounds 会被吞，控制器/几何/DOM 三方脱臼（fast-drag 变形同款根因）。

### 展开用绝对位移与回差带隔离系统拉回

启动恢复半藏位后，macOS 会在 show 时把探出屏右缘的窗口拉回屏内（实测最右屏右缘 4222→4174，恰好 48px）。这类系统 move 落在 48～72px 回差带内，只记录位置、不写窗也不展开；用户任一方向拉离超过 72px 才展开。这里不能再用“光标是否仍在窗口内”做闸门：`getBounds()` 在快速原生拖动中可能滞后一帧，光标闸门会把真实快拖误判成系统 move，随后反复钉回，造成“完全拖不出来”。

## 人怎么用

| 状态 | 外观 | 是否持久化 |
| --- | --- | --- |
| 展开 | 现有完整便签 | `bounds` 记展开位置和尺寸 |
| 横条 | 现有 40px 标题横条 | 不记；重启当展开 |
| 贴边 | 工作区左或右缘一枚 96×32 彩色书签头，静止半藏露 48px，悬停露整条；颜色跟随该便签 | 记 `dock.side`、`dock.y` 与 `dock.x` |

进出：

- 展开 ↔ 横条：现有收起按钮，行为不变。
- 横条 → 贴边：拖横条，左/右缘探出工作区对应缘 8px（光标顶到屏幕边，路过不误吸）时横条上显示「松手贴边」承诺提示（只发 IPC 状态，不写窗）；**物理松手确认后**才执行吸附——**吸附是拖出展开的逆运动**：窗口先一刀并集（横条 ∪ 目标矩形，新增区域全透明看不见），纸面用同族缓动 300ms 从横条矩形 clip 收成书签头并顺势滑到贴边点（与拖出展开的 clip 揭示同一套运动语言），演完主进程一刀裁成书签头窗口（纸面已占满，视觉零跳）。落位姿势按光标真相：光标还在书签头矩形上就落**露出**位（不再「先半藏再探出」两段动），不在则落半藏。松手时不在吸附区就什么都不发生。
- 悬停：书签头静止时半藏；鼠标悬上去整条 96px 滑出，移开滑回半藏。
- 贴边 → 展开：拖书签头（半藏或露出状态都可直接抓）。拖动全程跟手自由拖（move 流零写窗），**物理松手后按落点一次裁决**：水平离边达到 72px（48~72px 是竖拖手抖回差带）就在落点用上次展开宽高长开——过回差带的松手直接起播，不再先等 settle 拍；340ms clip 揭示时书签头替身钉在落点矩形上保留 ~120ms，纸面从其底下向外长，替身溶进标题栏——含甩上邻屏：在邻屏就地展开；不足 72px 则钉回（光标在窗上落露出位、不在落半藏位，一次到位；≤48px 直接落位、>160px 瞬移兜底、之间 180ms 滑行）。途中展开曾是窗口交接架构的「已知代价」（展开销毁书签头窗、拖拽会话中断），2026-09-01 被真机否掉后改为松手才展开。
- 过渡途中（吸附逆揭示 300ms / 钉回 180ms / 探头 180ms）随时可抓住窗口抢拖：物理按下即熔断当前事务、几何交还拖拽。
- 左边贴边往右长，右边贴边往左长，长开后夹进工作区，避免先冲出屏幕再回弹。
- 不允许展开 → 贴边，也不提供贴边 → 横条。

贴边时：没有按钮、不能缩放、不显示正文。书签头是该便签颜色的实心头，靠屏幕内侧两角使用与便签纸面一致的小圆角；有名称时在签上横排显示一小段（认得出是哪张即可），没有名称就是纯色头。

多显示器：吸到横条当前所在那块屏的工作区左/右缘，避开任务栏 / Dock；重启恢复贴回原来那块屏（`dock.x` 认屏），屏被拔掉后夹到剩下的屏上。

多张便签贴同一侧且书签头会重叠时，后贴的那张沿边向下错开至少 40px（签高 32px + 8px 间隙）；到底部不够错就向上找空位。实在没有空位，允许轻微重叠，但后贴的那张至少露出 24px 可抓高度。

## 窗口几何

**贴边态的书签头是一枚独立窗口**（2026-09-01 窗口交接架构）：固定宽 96、高 32，不可缩放，从创建到销毁尺寸恒定——可见时刻永不 resize，这是根除落定闪烁的不变量。便签主窗口在贴边态整体隐藏（保留 renderer 存活，展开时原位示出），只有书签头窗可见。休息位一半探出屏外：左缘 `workArea.x - 48`，右缘 `workArea.x + workArea.width - 48`；露出位整条贴边：左缘 `workArea.x`，右缘 `workArea.x + workArea.width - 96`。`y` 为拖入时横条上沿，再夹到工作区垂直范围内。多屏共边时隐藏半幅会漏到邻屏，退回 48 宽全露（书签头窗创建时即为 48 宽——尺寸在示出前定型，不算可见 resize，不留透明死区）。

横条与书签头都由原生拖窗整窗平移。拖动全程零写窗；吸附/钉回都在「松手 + 停稳」确认后执行——macOS 没有拖动结束事件（`moved` 是 `move` 的别名），松手由**物理按键监视器**权威判定（`CGEventSourceButtonState` 只读状态，8ms 轮询的 native helper 子进程流式上报 down/up；无需辅助功能权限；helper 崩溃/缺失时降级为「光标离开抓取点」启发式）：

1. 松手归属：物理按下时光标在窗口 ±4px 内才置位 `pressOnWindow`，物理抬起只处理置位窗——多窗并排时不会把别窗的松手当成自己的。
2. 松手后直接武装 settle watch（物理松手已是权威）：每 60ms 比对 bounds。**helper 活着时只要 1 拍**（松手已确定，60ms 只为确认拖拽尾部 move 冲刷完；光标判据不启用——松手后光标的跟随动作曾把收尾无限推迟，是真机「有时候松手要等一会儿才吸」的根因）；**helper 缺席/死亡时保持 3 拍**「bounds 没变 + 光标停稳 + 光标不在抓取点」，Windows 回退不能变脆。收尾——横条在吸附区 → `resolveDockYForWebContents` 预算错开 y 后执行吸附逆揭示事务（见下）；书签头位置有偏 → 180ms 惰性滑回钉边。比对期间窗口被系统动过（如 macOS 拉回屏内）或用户重新按住（isDown 每拍第一查）就不动。
3. 吸附逆揭示（窗口交接版，2026-09-01 定稿）：**可见运动全在 DOM，主进程只做一次 union 生长与一次窗口交接，没有裁窗**。①主进程先注册 `dock-shrink-ready` waiter，再发 `dock-applied`（`transitionId` + `shrinkFromStrip`）；renderer 用 `flushSync` 挂载持续存在的 overlay，显式像素钉住横条画面，paint 后回 ready。②主进程一次 `setBounds(unionAtSource/union)`（只长大，新增区域全透明，已验证不闪）；renderer 等尺寸与真实全局原点命中。③同一枚 overlay 300ms `clip-path + transform` 逆揭示到 bookmark，末帧书签头已钉在 target 全局点；paint 后回 `dock-shrink-finished`。④**交接取代裁窗**：书签头窗口（每便签一枚，96×32 恒尺寸，首次吸附前惰性创建并预渲染）在 target 矩形 `showInactive` 上屏——它展示的静态书签头与动画末帧同像素，重叠一帧不可见——主进程收到书签头窗的 paint ACK 后才 hide 便签窗；顺序永远是「先 show 已 paint 的新窗，后 hide 旧窗」，不出现两窗同时不可见的空帧。⑤主进程同步提交 controller（docked 态的原生几何操作对象从便签窗切换为书签头窗），并发 `committed:true`；磁盘保存仍走独立串行通道。三段 ACK 带同一 `transitionId`，timeout/epoch 变化/销毁在逻辑提交前统一 fail-closed 回横条。
4. 抢拖恢复同样属于这笔事务：旧 geometry waiter 的每帧回调先核对 active transaction，不能借共享 ref 重钉新事务；abort overlay 在横条视口恢复后才卸载。真实抢拖可能超过 500ms，松手恢复横条后的普通 `dock:null` 会重新武装 cleanup，避免 aborted overlay 永久残留。恢复义务记在 `pendingStripRestore`，活拖拽期间不写窗。
5. 原生阴影是窗口级而非 dock 级能力：所有便签在建窗时固定 `hasShadow:false`，运行中没有 `setHasShadow()`。书签头和 shrink surface 由 CSS 明确 `border:none`，稳定可交互的书签头使用一条不改变几何尺寸的轻微 `inset` 内描边；shrink surface 在整个事务期间（动画、union 平移、最终 native crop）不绘制 inset shadow——注意 `stable` 阶段（动画落位后）仍在裁窗**之前**，上一轮把描边挂在 stable 等于没移出 crop，闪烁照旧；现拆成 `--interactive`（pointer-events，stable 起）与 `--stroked`（内描边，仅裁窗 ACK 后的 `settled` 及 abort 回退挂），不使用 CSS 外阴影，也不再用动态开关原生阴影制造另一条竞态。**2026-08-31 17:35 真机验收证伪**：描边完全移出裁窗后吸附闪烁仍在，inset shadow 不是（唯一）根因；闪烁根因重新打开，剩余嫌疑为 overlay surface swap 首帧与第二次原生 `setBounds` 的 crop 中间帧，详见 HANDOFF。
6. 书签头拖动全程零写窗、跟手自由拖；**物理松手后按落点裁决**：水平离边达 72px（48~72px 是竖拖手抖回差带）→ 展开——**展开同样是窗口交接的反向**：过回差带的松手直接起播（不再先等 settle 拍；窗口还在追光标、瞬时不够 72px 仍走 settle）。便签主窗口在隐藏态先 `setBounds` 到展开矩形（隐藏时 resize 不可见、无闪烁），renderer 备好 reveal 首帧（clip 钉书签头矩形，沿用既有 expandFrom 机制），paint ACK 后 `showInactive` 主窗、再销毁书签头窗；揭示起播时书签头替身钉在落点矩形上保留 ~120ms，纸面从其底下向外长，替身溶进标题栏——含甩上邻屏：在邻屏就地展开；不足 72px → 钉回（≤48px 直接落位、>160px 瞬移兜底、之间 180ms 滑行）。
7. `sticky-notes:dock-applied` 是事务消息而不是“几何落定通知”：吸附先发带事务 ID / `shrinkFromStrip` 的 prepare，目标画面确认后再发 `committed:true`；展开带 `expandFrom`。renderer 负责同一 surface 与 DOM 动画，主进程单一拥有原生窗口几何、取消、controller 提交与持久化调度。悬停探头纯几何，不切 DOM。

## 数据

`NoteRecord` 增加可选字段，缺省等于未贴边：

```ts
dock?: {
  side: 'left' | 'right'
  y: number   // 夹取后的书签头上沿（屏幕坐标）
  x?: number  // 静止位 x：多屏认屏证据；旧记录没有，恢复退化为 y 距离猜屏
}
```

规则：

- `bounds` 始终表示最后一次展开态的位置和尺寸。进入贴边、沿边滑动，都不改 `bounds`。
- 从贴边展开后，用展开时夹取过的矩形写回 `bounds`，并删除 `dock`。
- 进入贴边时写入 `dock`，`side` 为命中的那一侧，`y`/`x` 为当前静止位；沿边滑动时 `dock` 经 bounds 变化防抖持久化跟随当前位置。
- 读取时：`side` 不是 `'left' | 'right'`，或 `y` 不是有限数字，则整段 `dock` 丢弃，当展开打开；`x` 不是有限数字只当缺省，不拖垮整段。
- 旧便签没有该字段，无需迁移。
- 启动时若有合法 `dock`：对每块屏的工作区各算一次候选贴边矩形，中心仍落在该工作区内的才可选；有 `dock.x` 时按 |候选.x - dock.x| 认屏（同名边每屏都有一条，y 距离常打平），否则按 y 距离猜屏。算不出任何可见候选则丢掉 `dock` 按 `bounds` 展开。

## 进程边界

- 主进程扩展现有 `note-window-collapse` 控制器，增加 `docked` 态和 `setDocked` / 启动恢复入口。**窗口交接架构下，controller 持有一个「当前活动原生窗口」句柄**：expanded/collapsed 时是便签主窗，docked 时是书签头窗；悬停探头滑行、钉回、settle watch 等几何操作对句柄透明，交接瞬间换句柄。窗口最小尺寸在贴边时作用于书签头窗（96×32 或共边 48×32），便签主窗保持现有 `NOTE_MIN_WIDTH` / `NOTE_COLLAPSED_HEIGHT` 或展开最小尺寸。
- **书签头窗生命周期**：每便签一枚，首次进入吸附预览时惰性创建（`show:false`，加载同一 renderer 包 `?view=tab&note=<id>`，只渲染书签头壳；建窗即定型 96×32 或共边 48×32），交接时 `showInactive`，离开贴边（展开/关闭）时 hide 或销毁。便签主窗在贴边态 hide 保活；关便签时两窗一起销毁。
- 三个态的窗口拖动都是原生 `-webkit-app-region: drag`；按钮、命名输入与命名热区保持 `no-drag`。renderer 不参与窗口移动，也没有 start/move/finish 拖动 IPC。
- 贴边恢复不能出生即贴边：出生就是小条 + 不可缩放 + 整页拖窗区的窗口在 macOS 上收不到任何 OS 鼠标事件（实测 enter/click 全丢），先按普通窗口创建、趁 show:false 改成贴边几何的窗口事件正常（与运行中新贴边的窗口同生命周期）。
- 原生几何全部在主进程：拖动中的 `move` 只做判定与预览（横条用 `resolveCollapsedDockSide` 判吸附区发 `dock-preview`；书签头用 `resolveDockedEdgeOffset` 判展开），横条拖动期间不写窗；写窗集中在松手后的吸附两刀事务、书签头惰性钉回与拖出展开三处。物理按键监视器是独立 native helper 子进程（`native/mouse-state.c` 编译为 `bin/mouse-state-darwin-arm64`，只读 `CGEventSourceButtonState`，8ms 轮询，stdout 流式上报；父进程死亡后 helper 8ms 内自杀，`before-quit` 兜底 dispose；崩溃/退出即降级，打包经 `build.mac.extraResources` 随包分发，仅 darwin）。阈值与矩形计算放在 `shared/note-dock.ts`，主进程与测试共用。任何过渡进行中（inFlight + epoch 代际令牌）忽略冲突事件，避免重入与旧会话迟到写状态。
- `sticky-notes:dock-applied` 同时承载 prepare、commit、abort 与展开通知。吸附 prepare 携带 `transitionId` / `shrinkFromStrip`，renderer 用同一枚 overlay 完成逆揭示并依次回三段 ACK；主进程同步提交 controller 后发 `committed:true`，renderer 保留同一 DOM 节点作为正式书签头。展开携带 `expandFrom`；无事务 ID 的 `{dock}` 只用于启动恢复或展开失败回滚。悬停探头不借道 `dock-applied`，也不演壳体过渡。
- 贴边态 renderer 只渲染环+芯书签头（可选横排名称），不挂载命名组件、工具栏或正文。
- 过渡失败或 `setBounds` 失败时，控制器回滚到进入这次过渡前的状态和窗口矩形，与现有收起失败回滚一致。不得留下 96px 宽却仍挂着完整便签 DOM 的窗口。
- 不把贴边几何写进 `personalization.json`，也不改系统窗口标题规则。贴边时系统标题仍用便签名或“悬浮便签”。

## 风险

- 初版 8×56 细缝在 Mac 真机上既难抓也不像便签；中间一版 36×96 竖胶囊又被真机否掉（"应该是横的"），现为 96×32 横书签头（宽 96 伸进桌面，高 32 沿边，明显扁于竖条），有名字露出一小段。再大就会重新挡内容，不再加大。
- macOS 工作区与菜单栏、Windows 工作区与任务栏必须用 `workArea`，不能用完整 `bounds`，否则会吸到系统栏底下。
- drag 区在应用非激活时收不到 enter/leave（悬停探头曾因此整面失灵），no-drag 区 leave 也非 100% 可靠——悬停进出都不能只信事件，必须以光标真相复核，露出期要有兜底轮询。
- macOS 在 show 时会把探出屏右缘的窗口拉回屏内（4222→4174，恰好 48px），会触发一帧非拖动 move；这类系统拉回必须被 48～72px 回差带吃掉。不能再靠“光标在窗内”区分：快速原生拖动时 `getBounds()` 会滞后一帧，光标闸门曾把真实拖出误判后反复钉回。
- 原生拖拽会话进行中争写 `setBounds` 两头都坏：写**被吞**一半 = 窗口在拖拽锚点与写入帧之间来回跳（抽搐），末帧被吞 = 定格半帧尺寸（184×36 变形那次）；写**中** = 窗口位置每帧被重置，「拖离 48px 展开」这类位移判定永远攒不到阈值（拖不出来）。多帧滑行同病。结论：move 流上任何逐帧写窗都不可行，滑行途中用户抢拖必须立即熔断、把几何交还拖拽。
- **bug 2（快速拖贴边抽搐/变形）已解（2026-08-21 过验收）**：根因是「磁吸不等松手」目标本身——几何改写必然落在原生拖拽会话进行中，写中被吞/写中必坏，三轮修补（snap + 校验补写、停歇钉回、release watch 光标启发式）都只是换姿势撞同一堵墙。终版改「松手才吸」：物理按键监视器（`CGEventSourceButtonState`，只读无需权限）给出权威松手信号，拖动全程零写窗，吸附/钉回全部推迟到松手 + 停稳后执行，拖动手感一次过验。教训：macOS 原生拖拽会话与 setBounds 写窗不可并发，「拖动中立即改几何」类需求只能把可见运动挪进 DOM（透明窗口）或推迟到松手。
- **动画手感三条实测真相（2026-08-21，阴影结论于 2026-08-28 收敛）**：①frameless + transparent 在 Mac 的 native shadow 会随几何变化由 WindowServer 重算；逐帧 `setBounds` 会「一格一格爬」，运行时 `setHasShadow()` 又会增加一次不受 renderer 事务约束的 compositor 切换。当前选择是在建窗时固定 `hasShadow:false`，以单一配置换取确定性；普通便签仍保留 CSS border / inset shading，稳态外观是否接受必须由真机验收，不能由自动测试代替。②大透明窗一帧 `setBounds` 拉满的首帧要分配 backing store，clip/遮罩必须在这帧之前就位（同 commit 隐身 + 占位书签头），否则用户先看到一闪纸面再开始动画。③clip-path（含 round）在 Chromium 常走主线程 paint，大窗每帧重绘超预算就丢帧，拉长时长（260→340ms）稀释每帧位移比换属性更安全——整壳 transform 会打废 `-webkit-app-region`（活拖拽红线），不能用。
- **「刚吸附落位马上拖不出来」（2026-08-21 修）**：吸附落位后 ~280ms morph 切 DOM，Chromium 对光标下的新书签头元素补发 mouseenter → 触发悬停探头复核；旧护栏只看 move 流/settle watch，不看物理按键——按下书签头、move 还没流第一帧的空档里探头滑行起跑 = 多帧写窗撞原生拖拽会话。修法：探头复核加 `isDown` 物理护栏，按住时记 pending、拖拽收尾用光标真相补复核。
- **三轮手感修复（2026-08-27 已实现）——「还是抽搞」的根因不是时长不是探头**：诊断日志实锤 `dock_tuck_glide` 出现 1925/2181/2392px 跨屏滑行。根因链：①`resolveDockedEdgeOffset` 带方向（右贴边只算往左的位移）→ 往屏缘外侧拖（多屏必上邻屏）永不展开 → 窗口被原生拖拽带出两千像素 → 松手后惰性钉回 180ms 跨屏拽回；②用户从 peek 露出态抓走时，钉回落回「露出」提交姿势，收尾 reconcile 发现光标不在又补一发 hide 滑行 = 两段动；③大多数吸附只挪 0~14px 仍演 120ms 滑行 = 黏腻。修法：位移取绝对值（任一方向 72px 展开，邻屏就地展开）；吸附/钉回落位姿势按光标真相一次算对（suppress 压制状态机——until-leave/边距/计时三层——整体拆除，它们没挡住根因因为根因是 tuck 不是 peek）；钉回 ≤48px 直接落位、>160px 瞬移兜底。阴影实验的最终结论不是「吸附时关、结束再开」，而是不能把 window-level shadow 当动画状态来回切；2026-08-28 改为建窗时一次决定。教训：「禁探头/调时长」多轮没服时就该怀疑滑行目标本身——日志里每次「抽搞」都有对应的几何事件，先读日志再动手。
- **落定闪烁根因定案（2026-09-01，GitHub 调研）：可见时刻改透明窗尺寸在 Electron 不可修**。Chromium 合成器跨进程异步出帧，WindowServer 几何同步生效，尺寸变化后内容帧晚 1~N 拍，中间帧透明窗露空。证据：electron 官方透明窗闪烁 issue 2017→2025 全 not_planned（#10069/#12130/#40830/#47527）、#42201 证明原生 resize 动画下内容同样慢几帧；escrcpy（Electron）、L2AutoHideWidget（Qt）、winautohide（AHK）、QQ/Snipaste/SideNotes 全部「恒定尺寸 + 纯位移」。三轮 DOM 时序补丁（时序/commitStyles/落地替身）全败与此互证。方案 A（union-rect FLIP）的动画段仍然成立并被保留——**唯一被废除的是最后一刀裁窗**，由窗口交接取代。新架构的剩余风险：①macOS 透明窗 show/hide 本身是否完全无闪（issue 集中在 Windows，Mac 真机待验；若有问题，备选是「停泊位」——不 hide，把便签主窗挪到屏外坐标）；②Windows 上 show/hide 闪烁更普遍，真机未验，备选同样走停泊位；③书签头窗与便签窗的焦点/置顶层级一致性（同 `alwaysOnTop` level + `showInactive`）。
- 贴边是第三态，收起动画的回归（基础态禁止 `height` 过渡、展开尺寸不得被 40px / 32px 写进 `bounds`）继续有效。
